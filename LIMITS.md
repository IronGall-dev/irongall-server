# LIMITS — what this server limits, why, and where it is weak

Every limit `irongalld` enforces, what it protects, who pays for it, when it is taken, and what is known not to hold. It is here to be checked: a way around one that § Known weaknesses does not list is reported privately (`SECURITY.md`); a cost one does not bound is an issue.

**These are this server's limits, not the protocol's.** The specification (`PROTOCOL.md` §8, in the client repo) says what a client must handle: a `429` with `Retry-After`, a few codes, and the promises every server keeps. How much, and of what, is each server's own choice; another server may limit differently. The reference clients obey whatever a server answers. **No value is written here:** each limit is a flag of `irongalld serve`, and `irongalld serve -h` prints its default.

## The rule

1. **No call with a pass is free, and nothing that reaches a table or a signature check is free.** Memory is cheap and the tables are not, but bandwidth can cost more than either, and a call that is cheap once can take a server down in volume. So every call a box makes spends from its budgets (a successful poll is limited for the bytes it moves, not for what it reads), and a call with no pass spends from its address's counts when it costs the server: a registration, a read that finds no box, a check that fails. **Every request is counted before anything is done for it.** A call that carries a pass this process has checked, of a box live in its memory, on a route that takes that box's pass, is its box's, and spends the box's budgets: the read of a box and a send take any box's, a call about a box only its own, and a box deleted or revoked, or whose current certificate is revoked, has no call that is its box's. Every other spends one budget of its address, sized for floods alone, at one gate in front of every route, before its route does anything: a call with no pass; one with a pass the process has not checked, whose parse and signature checks come after; a registration and a renewal, whose passes are read after their bodies; a revocation, the link page and a site's pages; and a request no route matches. Let's Encrypt limits every endpoint per address the same way, in front of its check of a request's signature. Until its pass is checked, a call is its address's. Before that count the server reads the request's head, to what the longest call needs, and hashes its `Authorization` value, and nothing more: what it costs is what reading those bytes costs. The budget is set far above what an honest crowd behind one address makes, which must never be refused; a box signs a new pass once in ten minutes.
2. **Who pays is who the call proves itself to be.** A call with a box's pass is the box's. New mail is its recipient's too. A registration, a read that finds no box, a check that fails, a call with no pass and one whose pass the server has not checked yet are the caller's IPv4 address's or IPv6 /64's: every IPv6 end site holds at least a /64. An IPv6 zone names an interface of the server's host and is no part of the address: a link-local caller is counted by its /64 too. A registration is its IPv6 /48's too, the range Let's Encrypt counts new accounts by.
3. **Cheapest check first, and what would change nothing is answered before what costs**: an identical retry, a statement no higher than the one held, anything for a revoked box.
4. **A count is reserved before the work it guards, and kept or given back after.** One checked first and counted after lets calls in flight at once all pass on one count. Where only the outcome says whether a call counts (a lookup that may find no box, a signature that may fail), the token is taken first and given back if the call turns out not to count; a refusal that only reservations still in flight would cause waits a moment for one to settle. Every reservation is settled however its call ends, a panic included.
5. **A box's counts are spent only by calls that showed its pass, and by mail to it that passed every check.** A stranger never spends one before a check that could refuse it: a count of the box's that a failed call could spend would be a way to lock its owner out.
6. **What an account may lift is volume:** what a box sends, what it receives, what it takes out, how large, and its calls. Registrations, revocations, lookups with no pass and failed checks are not for sale.

## How a refusal names its limit

Every `429 rate_limited` names its limit in `quota_id`, the name in the last column above, and whom it counted the call against in `subject`, `box` or `ip` (`PROTOCOL.md` §13). Where a box's own count in memory refuses a call, the server also reads the box's other counts the same call would spend, taking nothing from them, and answers with the longest wait, under that count's name, as RFC 8555 §6.6 asks: a renewal's calls and its renewals or certificates a day, and a registration's two counts. A count behind work (a read of storage, a signature check, the recipient's counts, and a send's sends a day, which only the dedupe shows a send would spend: a retry spends none) is not read ahead of it, so a caller can meet it once the first wait is over; the reason is the client repo's `PRECEDENTS.md`.

## The order of checks

Every route begins at its gate: a call that is its box's (rule 1) goes on to the steps below as its box's, and every other spends its address's flood budget there. A call about a box answers the box's state, from memory or one read, before its pass: deleted or never registered `404`, revoked `410`, its current certificate revoked `401`.

- **A send** (`PROTOCOL.md` §4.5; `send.go`): the sends before their pass → the pass → the sender's calls → the address and the query (its two serials) → the body, to its cap → an age file → the recipient exists and is active → the dedupe, so a retry is answered as the first send was whatever has changed since → whether the box takes new mail on this prekey from this sender → whether the recipient's ACL lets the sender in, before the counts that follow, so a refused send spends none of them → sends a day, the pair and box caps, the new mail received, each reserved → the write. The calls come before the dedupe so that the dedupe's read, which moved ahead of refusals that read nothing, is bounded.
- **A registration** (`register`): the gate, whatever it carries → the address and the query → the body's form and the identity's → a box this process holds, or a revoked address, is answered from what is held, unchecked but for an identical retry's pass, a miss reserved before it and the box's calls spent after it → the registrations counts, of the address and of its /48 → the statement's signatures → what is kept of the address (its revocations, and a deleted box's record), read with that count bounding it → the pass → the write.
- **A renewal** (`prekey`): the gate, whatever it carries → the address and the query → the body's form → the box's record → an identical retry, its pass checked and then the box's calls, answered from the record → the statement's place in the order, read without verifying: not above the current one, under an older certificate, or under one its identity revoked, refused with no signature check → a miss reserved → the signatures and the pass → the box's calls, a refusal of which reads the count below → the renewals count or, under a later certificate, the certificates count, which one while the current certificate is revoked skips → the write.
- **A revocation** (`revoke`): the gate → the address and the query → the body's form → what is held of the address, its record and its revocations → anything for a revoked address `410`, with no check → a revocation of certificates through a serial no higher than the one held, answered before its signature → for an address the server holds nothing of, the registrations counts → a miss reserved → the signatures → the count of raises, for a raise → the write.
- **A lookup** (the read of a box, `GET /v1/<address>`, and `GET …/revocations`): with a pass, the pass and then the box's calls; with none, nothing but the gate; then the address and the query, then the box from memory or one read, a miss reserved before it.
- **Putting an ACL** (`putACL`): the address and the query → the box's state → the pass → the box's calls → the body, bounded from `-acl-entries` → its form, then its entries against `-acl-entries` → the box's record → a version not above the one held, `409 conflict` → the write → the box's unacked mail from what the deny list matches deleted, only if memory shows the box holding any. **Reading it** (`getACL`): the address and the query → the box's state → the pass → the box's calls → the record.
- **Any other call with a pass** (`list`, `fetch`, `ack`, delete, adopt, leave): the address and the query → the box's state → the pass, a miss reserved if the process has not seen it → the budget the call belongs to.

## Accounts: where a box's limits are read

`limitsFor` reads a box's account, from a cache, and returns its limits. Today one kind of account lifts anything: an unmetered one, whose boxes have no daily send limit, the largest size cap, and no budget of calls or of new mail, in or out. A box in no account is known to be so from memory, with nothing read.

**What is planned for paid volume, and not built:** an account carries a value for each volume lever (sends a day, calls, new mail received and taken out, the size cap) and a price; `limitsFor` applies the account's values to its box, as a sender and as a recipient; a budget other than none needs its own bucket for each set of values. Nothing else is to be sold.

## Known weaknesses: read these first

1. **Every budget and count is per process,** in memory, and so are the cursor each box was handed last and the sends in flight. With N processes a box can spend N times each, and a restart starts every box afresh (the numbers a day included). Only the pair and box caps are shared, through the stream, a second or two behind. Routing each box to one process, or sharing the counts, is not built (#55).
2. **The budget of new mail received is shared by every sender, and it is on by default.** Enough senders can spend a box's, and delay everyone else's mail to it; the mail waits in the senders' outboxes and is sent again. Every sender's own counts bound how much each spends. It is kept on, beside the budget of mail taken out that only the box spends, so the server leans to refusing a flood at the door; either can be set apart, or off. **A box whose address is published can be delayed this way by a determined enough sender: keep the address of a box you rely on private** (the specification's §8, lever 1). A box's ACL with an allow list (the specification's §6.2) lets a published box take mail only from the senders it names: the refusal comes before the budget is spent.
3. **An address is a coarse key.** Honest boxes behind one address (a NAT, a cloud's egress) share its registrations and its misses. Their calls with a pass are their own, but for three things that count against the address whatever a call carries: naming a box that does not exist, a check that fails, and a pass the process has not checked yet, which spends the address's flood budget before it is checked, once in a box's ten minutes. A box's lookups of itself carry no pass (the specification's §4.1), so they are the address's too. An address that has spent its misses has its next new pass refused until one comes back; a pass the process has seen is unaffected.
4. **What is answered from memory to anyone is limited only by the flood budget of its address** (`-request-burst`), which is set far above an honest crowd's use and so lets through a great deal before it refuses. So are the checks of passes the process has not seen, at up to two signature checks for each call that budget lets through: a box that signs a new pass for every call has as many checked as its address's budget allows, and each IPv6 /64 has a budget of its own. Each such answer costs this server only its bytes, but for the read of a box that exists and is not in the record cache (`-box-cache`), which costs one GetItem; cycling past the cache takes more real addresses than it holds, which nobody can find by guessing. A connection that never completes a request spends nothing. Until the client repo's #214, a box's read of another box carries its pass and spends the box's calls; after it, that read is one of these.
5. **A pass is checked once in each process,** at two signature checks; after that it is a lookup in memory.
6. **The one large read can still be held for as long as a body takes at the minimum rate:** for a body of the largest cap, hours. Only a box whose account lifts its cap can take it, and a send waiting for it gives up after `-body-timeout`.
7. **Nothing bounds how many sends wait for the large read,** and each holds the free size it has read while it waits.

## The operator: clearing an address, and who spends a limit most

`irongalld limits clear -socket PATH -ip ADDR` forgets what the limits keyed by an address hold of one caller, as if it had never been seen: its misses, its registrations, its sends before their pass and its calls with no checked pass. An IPv6 address, with or without a zone, is cleared by its /64, as it is counted, and its registrations by its /48 too. It answers `{"address": <the key cleared>, "cleared": [<the names of the limits that held anything>]}`. A box's own budgets are not touched.

`irongalld limits top -socket PATH -limit NAME [-n COUNT]` lists the keys one limit holds deepest in debt now, deepest first: which box takes the most new mail (`mailbox_busy`), which address registers the most (`registrations`). A limit is named as a refusal names it: a `rate_limited`'s quota, or the code of its own (`mailbox_busy`, `fetch_paced`, `refetch_spent`). It answers `{"limit": NAME, "keys": [{"key": <a box's address or a caller's>, "full_in": <seconds until its bucket is full>}]}`, reads memory and keeps nothing. How often each limit refuses is the metrics' (`ARCHITECTURE.md` § Metrics); which key it refuses is no metric, since an address or a box is no label.

Both go through the running server's `-admin-socket`, because the counts are in that process's memory and a process of its own could not reach them; so each sees one process's (weakness 1). The socket is a Unix socket the server makes 0600 from its bind on, never on the API's listener; put it in a directory no other user can write, since one who can may replace it. The server logs that a command ran and which limits it touched, never an address or a box.

## Tested

Each limit, each order above and each refusal's name is held by the tests in `internal/server/` and `cmd/irongalld/`, whose names say which, `TestEveryRequestIsCountedBeforeAnythingIsDone` the rule. They run on the in-memory store, and on DynamoDB with the test tables set (`AGENTS.md`).
