# PROTOCOL-SERVER — what this server does behind the spec

**The protocol's specification is [`PROTOCOL.md`](https://github.com/IronGall-dev/irongall-client/blob/main/PROTOCOL.md) in the client repo:** the wire, the checks and the refusals, as a client meets them. Every `PROTOCOL.md §N` in this repo's docs and code means that file. **This file holds how this server does each step** (storage, memory, measurements), under the spec's own section numbers. Read the spec's section first: a line here is a note beside it, not the whole of it.

**A change to the wire or to what a client meets is made in `PROTOCOL.md`, with the client code;** a change to how this server does it is made here.

## §0a, Terms

- **Identity key types:** the server registers the key types `-identity-types` names, of those this build verifies (`protocol.IdentityTypes`). `ssh-ed25519` is always one of them: the server does not start without it.
- **Address / `H`:** the box identity — the SHA-256 of its identity document (§2). As text, 64 lowercase hex characters; in DynamoDB keys, the 32 raw bytes. `H_A` is the sender, `H_B` the recipient. **One identity key ⇔ exactly one address.**
- **Header:** three different things. The **header item** is the per-message DynamoDB item (§7); the **age header** is the text head of an age file (§4.3); **HTTP headers** are HTTP headers.
- **The live prekey** is the current one: the server checks a message's stanza TYPE against its type (§4 step 7). The server keeps the newest retired prekeys' key hashes (`-retired-kept` of them, a service limit) only to refuse a key that comes back.
- **The link page** (`/to/<address>`, `link.go`) names the server that serves it, in the link it gives and in its command: by the name the request calls it by when that is one of `-names` (written as §6.1b writes it), else by the first of them, and by the scheme the caller reached it by: `https` over TLS to the server, otherwise what a trusted proxy (`-trusted-proxy`) says in `X-Forwarded-Proto`, which TLS ending in front sets to its client's scheme (Cloudflare does, and overwrites a client's own), otherwise `http`. A proxy in front must pass `Host` and that header on unchanged.

## §0b. A body is read as every reader reads JSON

- **Every JSON request body goes through `decodeJSON`** (`internal/server/server.go`), which is the client repo's `protocol.UnmarshalRequest`: the same code the clients read answers with, on Go's `encoding/json/v2`. So the server and the clients hold one set of rules (`PROTOCOL.md` §0b) by one implementation. A byte field not in its one encoding is `bad_encoding`; anything else that breaks a rule is `bad_request`, and an unknown member is named in `member`.
- **A send's body is no JSON:** it is the ciphertext's bytes, read as they come whatever the `Content-Type` says (§4, step 3), so no JSON or base64 is read on a send, and none written on a fetch (§7).
- **A query is held to its call's parameters** (`pathAddr`, with the address in the path): `protocol.ParseQuery`, each parameter at most once and no other. One the call does not take, or one given twice, is `bad_request` with its name in `member`, as an unknown member of a body is; so is a send's serial or a list's cursor not of its form. Only the send (`prekey_serial`, `certificate_serial`) and the list (`cursor`) take any.

## §3. Registration: steps 4 to 9 as this server does them

- **Step 4, the key's type:** `protocol.ParseIdentity` answers for the document's form, for a key type the protocol does not define, and for the key's checks. A key type that is not on this server's list is then answered `unsupported_key_type`, with the list in the detail. The list is of what the server can verify: it checks the identity's signature on every certificate it puts on record.
- **Step 5, before anything that costs** (`LIMITS.md`): a box this process holds is answered from its record (`Store.Known`), with no signature checked but an identical retry's pass, and that only once the box's current certificate is not one its identity revoked (`401 certificate_revoked` otherwise, as `PUT …/prekey` answers the same statement). Any other registration takes from its address's registrations here, by its IPv4 address or IPv6 /64 (`-registrations-per-hour`) and by its IPv6 /48 (`-range-registrations-per-hour`), and those counts are what bound the signature checks after it: they reserve no count of misses of their own. An address its identity revoked is answered `410` from what memory holds the same way.
- **Steps 6 and 7 cost four signature checks:** the identity's on the certificate and the working key's on the statement (`protocol.VerifyPrekey`), then the pass, checked as every pass is (§6.1b): the working key's signature on it, and the identity's on the certificate once more. An identity's key type changes only the checks of its own signature: 58 µs each for Ed25519 and 81 µs for P-256 (measured 2026-10-13). A post-quantum statement's key check adds a trial wrap, an ML-KEM-768 encapsulation.
- **Step 6, the times:** a certificate that began less than `protocol.PassLifetime` before the server's now (the furthest behind its own clock a box it takes may be, so every certificate it takes has begun for every reader it takes), or has ended, and a statement that has expired or ends more than 33 days and an hour from the server's now (`protocol.MaxPrekeyLifetime`: an hour past what a client asks for, `PROTOCOL.md` §0), are `prekey_time`, and the answer is dated by the server's clock as every answer is. A client makes both with an hour of room, so one of these is nearly always the caller's clock, and the hint says which way.
- **Then what is kept of the address** (`PROTOCOL.md` §3, step 6): its box's record and its revocations, from memory or by one Query of the address's items (§7), which the count of registrations bounds. A certificate the identity revoked is `401 certificate_revoked`, box or none; while a deleted box's record is kept, a certificate no later than its last is `401 certificate_not_current`.
- **Step 8, a new box:** DynamoDB `PutItem` of the box's record with `state: active`, the certificate's serial and the SHA-256 of its bytes, and its expiry (`expires_at`, §7), condition `attribute_not_exists(addr)` → `201 {}`. One write, and the box is in use: no call of its owner is needed first. **A deleted box whose record is kept is undone instead** (`undelete`): the new statement is taken as a renewal's is (§6.4; a key the box published before is `prekey_not_new`), the state is `active` again and the expiry moves, in one `UpdateItem` conditional on the record's revision → `201 {}`. Its ACL and its account are the record's, and stay.
- **Step 9:** the record's `cert_serial` and `cert` are what later calls are held to (§6.1b, §6.4). Both are written with the statement they come from, in the same write, and so is `senders`: the sender key types the box declared with that statement (`PROTOCOL.md` §2c), of which the server keeps the names this build verifies, or `any` alone.

## §4.3a. Padding: the size limits are checked by hand

- **The server does nothing, and a size limit must be a whole number of its own blocks.** As sizes go, 64 KiB and 10 MiB are such numbers and 100 KiB is not: a message just under a limit like that one would be padded past it. With limits chosen that way a client never needs to know the limit. 🛑 Nothing checks this when `irongalld` starts: check `-max-size` and `-account-max-size` by hand before changing either.

## §4. The send pipeline: steps 1 to 3 and 5 to 9

- **Step 1. The pass, before the body is read, and then the sender's calls.** The pre-auth rate per IP is taken first (`-sends-per-minute-per-ip`; an edge in front may have applied its own). Then the pass is parsed for the box it names, that box's standing is read (its state, its identity's key and its current certificate's hash: from memory if this process holds the box, otherwise from its record, §6.1b), and the pass is checked. The sender's record is then read for its account, from the record cache (the LRU of box records, `-box-cache`) or one `GetItem`: a pass that verified names a box that exists, so this read is not one `-misses-per-minute` counts. Then one of the sender's calls is spent (`-call-burst`, `LIMITS.md`), a retry's included: it bounds every step after it, the dedupe's read among them. A sender in no account is known to be so from memory, and spends it with nothing read.
- **Step 2. The address and the query, before the body is read:** `B` in the path, 64 lowercase hex characters (`bad_address`), then the two serials in the query, each once and written as a statement writes one, and no other parameter (`bad_request`, naming the parameter in `member`). Both cost nothing to check, so a send that names no box or no prekey reads no body.
- **Step 3. The read limit is the sender's own cap**, which counts the ciphertext's bytes, and the body is those bytes. A `Content-Length` past it is `413 too_large` before anything is read, and a body that runs past it while it is read is the same, both with the cap in `limit`. A body past the size of the free cap (`-max-size`) waits for the one allowance for large reads, and holds it until the send is answered: it bounds memory to one body of the largest cap. Only a sender whose account lifts its cap ever asks for it, since anyone else's body is refused at the free size. A body that stops coming is cut off by `-body-timeout` and `-body-min-rate` (this repo's issue #7, `LIMITS.md`).
- **Step 5. Is `B` registered and ACTIVE?** A lookup in memory, DynamoDB only on a cache miss, which reserves a count of misses for the caller's address (`LIMITS.md`). `B` unknown or deleted → `no_such_mailbox`; `B` revoked → `revoked`.
- **Step 6. The dedupe:** one `GetItem` of the message item `box, id`, before anything about new mail is asked, so a retry gets its original receipt whatever has changed at `B` since. The read is bounded by step 1's calls, and a retry spends one.
- **Step 7. New mail on this prekey.** `B`'s current prekey past its `not_after` → `prekey_expired`, and the same for a current statement under a certificate `B`'s identity has revoked (§6.3a). That check parses the revocation of certificates in `B`'s record, so only a send to a box that has one pays for it.
- **Step 8. First the recipient's ACL** (§6.2), from `B`'s record, which step 5 holds: a sender its deny list matches, or its allow list does not, is `403 sender_not_allowed`, in one wording for both. It comes before the counts, so a refused send spends none of them. **Then the counts, each reserved before the write and given back if nothing is stored:** the sender's sends a day (`rate_limited` naming `sends`); the pair and box caps, read from memory (not reserved: `LIMITS.md` § Known weaknesses); and `B`'s budget of new mail (`-receive-burst`), from all senders together, read with `B`'s account → `mailbox_busy`. An unmetered recipient has none.
- **Step 9. Write, body first** (§7): S3 `PUT` the body, then the message item, conditional on no live item with this id. Two plain writes, not a transaction.
  - If the condition fails, a concurrent send of the same ciphertext got there first. Answer as step 6 does.
  - Any other failure answers 5xx. The client keeps the message in its outbox and retries; the retry writes both again.
  - Then update memory, keep the counts step 8 reserved, and answer `201`.

**Step 7, the sender's key type, costs no read of its own.** The sender's type is line 2 of its identity document, in the record the send already holds for its account; what the recipient declared is in the recipient's record, which step 5 loads. A sender on an `ssh-ed25519` identity is never refused here.

**No signature on a message is checked on a send, and none is stored:** it is inside the ciphertext (`PROTOCOL.md` §4.4). What a send costs the server in signature checks is its pass, and only the first time that pass is shown (§6.1b).

## §5.1 and §5.7. Polls, pages and repeat fetches

- **Every list answer carries the poll interval in `Retry-After`,** `-poll-after` seconds, a `304` among them (RFC 9773 §4.3's use of the field). Bots are told that interval; what is enforced is `-poll-burst` at once and one more every `-poll-refill` (§8).
- **A first page carries an `ETag`: the first 16 bytes of the SHA-256 of its body, in hex** (`writeList`). It is a strong validator that every process computes alike, with no key, and it changes with any message that enters or leaves the page or the count; a page that holds mail cannot be made to share an empty box's, the tag a client keeps, short of a 128-bit second preimage. An `If-None-Match` that names it, weakly compared, is `304` with no body. The field is read by `protocol.IfNoneMatch`, as RFC 9110 §13.1.2 has a server evaluate it: `*` only as the whole value, each listed tag through its closing quote, and a value of any other form names no page. A split at commas once let one tag holding `,*,`, which a client keeps, make every poll of the box `304`. A page after the first carries none. An empty poll never leaves the process either way: the empty page, and so its tag, is built from memory's count.
- **A cursor is base64url, unpadded, of the last key listed** (`formatCursor`): one or more of `[A-Za-z0-9_-]`, as a client holds it to (`protocol.CheckCursor`). One that does not decode to a key this server could have handed out is `400 bad_request`, naming `cursor` in `member`, before the pass is read (`PROTOCOL.md` §5.1).
- Check the pass (§6.1b): for a box this process holds, from memory. **The per-box poll rate applies to EVERY poll, empty ones and `304`s included** — an in-memory token bucket, taken before `If-None-Match` is read, so a box that polls too often is told `429`, never `304`.
- **A list with a cursor is a continuation only if the box holds mail after the cursor, and the cursor is the one this process handed the box last** (this repo's #5): any other, made up, replayed or a retried page whose answer was lost, is charged as a poll and answered all the same. Serving a cursor's page replaces it with the next page's, and the drain's last page clears it. A continuation takes from the box's page allowance, not its polls: two full boxes' worth of pages at once, a full box's worth back every `-poll-refill` (the time one poll takes to come back, not the poll interval), so a drain is never refused (§8). With nothing after the cursor it is a poll: it takes from the poll rate and is answered from memory with an empty page. So a cursor is no way around the poll rate.
- **If the in-memory count is 0, answer the empty body and touch nothing else.** An empty poll that carries a pass the server remembers measured 33 to 34 µs of server CPU, over loopback HTTP on one core, access log included; the same poll with the 62-byte bearer token it replaced measured 31 to 32 µs on the same machine (2026-10-13, `bench/README.md`). The check of the pass itself is 1.5 µs of that. That figure predates `6a7f0ca`, which redacts each log line whole with a regexp and quotes the path: the access line measured 3.3 µs, against 0.5 µs for the segment redaction it replaced (a benchmark of the line alone, 2026-10-20). The poll itself was not measured again.
- Otherwise the page comes from one Query of the `live` index of the messages table (an in-process listing layer is planned and not built, `ARCHITECTURE.md` § Memory) — small entries keyed by `received_at`, so the Query returns time order and the cursor is the last key (§7). Small entries, because **DynamoDB bills a Query by the full size of each item read, projection or not** (AWS docs). → `ARCHITECTURE.md` § Memory.

**5.7 Ack:** `DELETE /v1/<B>/messages/<id>` deletes the S3 body and takes the message out of the list, and the counts follow. Its item stays as the dedupe record until the TTL. **Reading does NOT delete** — delivery is at-least-once, and unacked mail expires at the TTL. **But a message is meant to be fetched once and kept by its reader**: a message's first fetch spends the box's budget of new mail taken out (`-drain-burst`, `-drain-refill`; reserved before memory counts the fetch, given back when it was not a first one), and a fetch of one the box has fetched before takes from an allowance of `-poll-burst` at once and one more every `-poll-refill`, the box's alone and apart from its polls; past the first, `429 fetch_paced`, and past the second, `429 refetch_spent`, each with `Retry-After`. Both clients store a message and ack it at once, so they meet the allowance only after a failure. The count is kept per process and a restart forgets it. The ack answers `204 No Content`. **A fetch or an ack of an id the box does not hold** is `404 no_such_message` from memory, and spends one of the box's calls (`LIMITS.md`): a held message's fetch and its ack were paid for by its receive.

## §6.1b. The pass, as this server checks it

- **What memory holds of each box it has loaded, for this check:** the box's state, its identity's key in SSH wire form (51 bytes for Ed25519, 104 for P-256) and the SHA-256 of its current certificate. With them a pass is checked with no read. The record itself holds the same, and is what a box this process has not loaded is checked against.
- **Before anything else, a value longer than any pass can be is refused,** `401 unauthorized`, before it is hashed or parsed: `protocol.MaxPassAuthorization`, 5,600 bytes, the length of a pass in the form a client writes whose signature is the most any identity key type's bound allows, whitespace a sender adds counted too (`protocol.MaxSignature`; `PROTOCOL.md` §3, §6.1b), since the box, and so its type, is not yet known. The type's own bound is held once the certificate on record names the identity (`Pass.VerifyUnder`). A pass is 1,264 bytes. Go's own limit on all of a request's headers, 1 MiB, still applies to what is read.
- **So is a call with two `Authorization` lines, or more** (`authorization`): which of them is the pass is not for the server to choose, so the call carries none, and is refused as one that carries no pass is, a pass the server took a moment ago in either line included. A lookup with two is not one with none.
- **A new pass is checked in three steps, cheapest first** (`checkPass`):
  1. **The certificate it carries, by the SHA-256 of its bytes, against the hash of the box's current one.** A pass under any other certificate is refused here, with no signature check. Another encoding of the same certificate, which one signed by an ECDSA identity has (`PROTOCOL.md` §2b), is other bytes, and is refused here too.
  2. **The working key's signature on the pass.** A certificate is public, since it rides in everything a box signs, and a signature does not cover the key it names: anyone can name a box's certificate in a pass of their own. This step is what refuses that.
  3. **The identity's signature on the certificate, and every rule of `PROTOCOL.md` §2b's table,** as when the certificate was put on record. It is reached only by a pass the working key signed. It checks again what a registration or a prekey upload checked, so a record that held the hash of a certificate its identity never signed would still give no pass. If it ever fails, the record is wrong: the server logs it and answers `401` with the hint to publish a new prekey, which is checked in full.
- **A pass that passed is remembered until it runs out, or until its certificate ends if that is sooner:** per box, the SHA-256 of the pass in the one form a client writes it (`Pass.Authorization`), the certificate it was checked under, and that moment. A later call with the same value, while the box's current certificate is still that one, is a hash of the header and a lookup: 1.5 µs measured. The same pass in another form a server reads (`PROTOCOL.md` §6.1b) is a parse, a second hash and the lookup, and no signature check, so a pass costs one check however it is written. The first check is those three steps, two signature checks in all: about 180 µs measured (`internal/server/cost_test.go`). So a box that keeps its pass for ten minutes, as both clients do, costs one such check in ten minutes of calls.
- **One pass is remembered per box, the last it showed.** Two clients running one box with different passes would each be checked again on every call; the clients here keep one pass in the box's state directory.
- **A pass that has run out is never taken again, and its entry is dropped at the next sweep,** which runs when a pass is kept and at most once an hour. So the map holds only boxes that showed a pass within about the last two hours. It is 168 bytes a box (measured).
- **The server's names are a setting, `-names`:** a pass is checked against the request's `Host`, and only if that is one of them. The name is not sent with the pass, so a server that took whatever name a request gave would take a pass made for another server. A proxy in front must pass `Host` on unchanged. `--dev` takes any name unless `-names` is given. A pass the server remembers was checked this way when it was first shown, and is taken after that whatever `Host` a later request carries.
- **`Host` is written as an origin is, as a client writes the server's name in its pass** (`serverName`; `PROTOCOL.md` §6.1b): lowercase, its port as a number, and no port at all when it is 443 or 80. TLS ends in front of this server, so it cannot tell which scheme a client called it by, and drops either default: a box whose URL is `https://irongall.dev:443` signs for `irongall.dev`, and its call may name `irongall.dev:443`, which this server reads as `irongall.dev`. A client that calls `https` on port 80, or `http` on 443, names a port this drops, and its pass is refused. So each of `-names` is written that way too: with a port only when it is not the default.
- **The order of the answers, for a call a box makes about itself** (list, fetch, ack, delete, adopt, leave): the address in the path and the query first (`400`, §0b), then the box's state (`404`, `410`), then the pass, so a call naming a box that is closed or revoked is told so whatever it carries. A box whose current certificate its identity has revoked (§6.3a) is answered `401` next, before any pass is looked at. **A send** has to read a pass to know whose it is, so one that is not a pass is `401` first; then its box's state answers (`403 unknown_sender` or `sender_revoked`), then the pass, and only then its address and query (§4, step 2). **A registration** follows the spec's order: the statement, the pass, then whether the box exists. **A prekey upload** answers first for a box that does not exist or is revoked, then for the statement, then for the pass.
- **Run out, or running out more than an hour ahead,** is `401 pass_expired`, and is decided before any signature is checked, as is a certificate that has not begun or has ended. The hint says which way the caller's clock is off if a new pass is refused too: 10 minutes or more behind, or more than 50 ahead (`PROTOCOL.md` §0). The hint says to check that clock, never to set it by the server's. **Every answer is dated by the clock the checks read** (`Server.dated`), so a client can set the `Date` beside its own. A pass under a certificate that is not the box's current one, or under one whose record does not verify, is `401 certificate_not_current`, with the current one's serial in `certificate_serial`; one under a certificate the identity revoked is `401 certificate_revoked` (§6.3a). Anything else wrong with a pass is `401 unauthorized`: not a pass, another box's, made for another name, a signature that does not verify.
- **A pass this process has not seen reserves a count of its caller's address first** (`-misses-per-minute`, `LIMITS.md`), kept if the pass fails and given back if it passes, and so does an `Authorization` value that is no pass: past the count, a new pass is refused before it is checked. One the process remembers is not counted. One under any certificate but the box's current one stops at step 1: 35 µs measured, a parse and two hashes. One that carries the box's current certificate, which every correspondent of the box has seen, stops at step 2: 95 µs, one signature check. A registration's pass is bounded by the count of registrations instead (§3).
- **Multi-process:** a box's move to a new certificate reaches the other processes through the DynamoDB stream (`ARCHITECTURE.md`; 1 to 2 s). Until it does, a process still takes a pass under the certificate before it. That window is stated, not hidden.

## §6.2. The ACL, as this server keeps it

- **It is part of the box's record** (`acl`, §7), as the document `GET …/acl` answers, and so it is in the record cache (`-box-cache`) with the rest of the record: a send's check of it (§4, step 8) reads nothing that step 5 had not read. In memory it is two sorted lists of addresses, 32 bytes an entry, searched by halves.
- **`-acl-entries` bounds it, its two lists together,** because a record with its ACL sits in the cache and every write of the record pays for its size: a renewal writes the whole record. The body of a `PUT` is bounded from the same flag before it is parsed, and a body over that bound is answered as an ACL over the entries is, `413 too_large` with the entries in `limit`. With `-acl-entries` off, the body is bounded only to keep the record one item, and `limit` is that bound's bytes.
- **`PUT …/acl` replaces it whole,** with one write conditional on the record's revision as every other is, and only with a version above the one held (`409 conflict` otherwise; a box with none is at 0). Nothing removes one: an ACL allowing `*` and denying nothing lets everyone in, as no ACL does.
- **Then the box's unacked mail from every sender the deny list matches is deleted** (`DeleteFrom`), as acks delete it: bodies first, then each item leaves the list, found by one Query of the live index, which carries each message's sender. It runs only when memory shows the box holding mail. A send that passed the check just before the write can still land after the delete; the next `PUT` that denies its sender deletes it, or its recipient's client drops it.
- **`GET …/acl`** answers the record's, or for a box that has put none, version 0 allowing `*` and denying nothing.
- **Multi-process:** as a revocation (§6.3), the change reaches the other processes through the stream, and until it does one that holds the box answers sends by the ACL it had.

## §6.2. Delete, as this server does it

- **`DELETE /v1/<A>`** (`deleteBox`), with the pass: the box's unacked mail is deleted first (`DeleteMessages`), then its record is marked `state: deleted`, its expiry set to the end of its current certificate, which the signature of its stored statement carries: one `UpdateItem` conditional on the record's revision → `204`. The box is then answered as one with no record, `404` to every call that names it and `unknown_sender` to a send under its pass, from memory as every state is.
- **The marked record stays until DynamoDB's TTL deletes it,** some time after its expiry (§7), and until then a registration is held to it and undoes the delete (§3, step 8). Its ACL and its account stay with it, so an undone delete restores both, and the index of each account's boxes lists it until the record goes.
- **Multi-process:** as a revocation (§6.3).

## §6.3. Revocation, as this server does it

- **The route checks in this order** (`revoke`): the body's fields; that the document hashes to the address in the path; what is held of the address, its box's record and its revocations, from memory or by one Query of the address's items. **Then, before any signature is checked, what could change nothing:** anything for an address already revoked is `410 revoked`, the body unread beyond its form. Then one signature check, `protocol.VerifyRevocation`, the function a client runs, a miss reserved before it and kept if it fails (`-misses-per-minute`, the caller's address's). No pass is read.
- **For an address this server holds nothing of,** the call also takes from its address's registrations (`-registrations-per-hour`, and `-range-registrations-per-hour` for its IPv6 /48) before any signature is checked: keeping a record for good is what a registration costs, and that count is the bound on what anyone can make this server keep, one new identity at a time (`LIMITS.md`). A revocation for an address with a box, deleted or not, or with revocations kept already, takes none.
- **A signature check reserves a count of the caller's address first** (`-misses-per-minute`), kept if the body does not verify and given back if it does: it costs a check that nothing else paid for. Past the count, a caller is refused before the check, a revocation that would have verified included, until a count comes back. The revocation of an address is counted by nothing else.
- **The revocations item is written first, then the box's mail, then its record** (`Revoke`, `DeleteMessages`, `DeleteBox`): one `UpdateItem` of the address's revocations item (§7) that keeps the signature once (`if_not_exists`), served by the read of the box as the record's `revocation_signature`. A send that had passed its recipient check before the write can still land after the delete. It is never served, since every call naming the address now answers `410`, whatever is left of its record, and it goes at its expiry. Anything sent again for the address is `410`, and deletes again only what memory shows is left: its mail while memory shows the box holding some, and a record left beside the revocation, by a delete that failed or a registration that raced the revocation, which is never served and which its TTL takes in any case. One sent back at an empty box, in whatever bytes, draws no read of the messages table.
- **The signature is kept in the address's revocations item for good,** with the identity document, box or none, and the read of the box, `GET /v1/<address>`, serves the two as the record a `410 revoked` carries. Nothing about a revoked address lives only in the memory of the process that took the revocation: another process, or this one after a restart, serves the same record (tested on DynamoDB).
- **This server is a revocation server** (`PROTOCOL.md` §6.3, "Revocation servers"): it answers that role's read, `GET /v1/<address>/revocations` (`getRevocations`), with no pass and limited as the read of a box with none is (by its address's flood budget, `-request-burst`, and a miss for an address it holds nothing of), from the same record and cache as that read: the record it keeps of the address, or `404 not_revoked`. A box needs the route only of a server it lists as one; its own server's read of a box carries the same. It keeps and serves one for any address, box or none. It has no mode with registration and mail turned off. A client publishes to each server it lists by itself, and this server passes a revocation on to nobody.
- **A client's read of a box before a post** (`PROTOCOL.md` §4.1) costs no read of the boxes table that a send did not already cost: it is answered from the record cache, and what the record keeps of revocations is served as it is kept, with nothing parsed. For a box this process has not loaded, it makes the one read that the send after it would have made, and the send is then answered from memory. It is counted against the box whose pass it carries, or against its caller's address with none (`LIMITS.md`).
- **Multi-process:** the change reaches the other processes through the DynamoDB stream, as a new certificate does (§6.1b): the revocations item's image adds to what each holds, and the record's deletion makes each forget the box, whose next use reads it again. Until it does, a process that holds the box in memory still answers for it as it was.
- **Every answer under `/v1/` carries `Cache-Control: no-store`** (`notStored`), so nothing in front may serve a box's identity, its prekey or a `410` again. A `410` is cacheable by default.
- **Not built:** a standalone index.

## §6.3a. Certificates revoked, as this server does it

- **The same route, and the same order of checks** as §6.3 (`revoke`): the body's fields, which are the document and then a revocation of certificates with its signature, a revocation of the address, or both; that the document hashes to the address; what is held of the address. **A revocation of certificates through a serial no higher than the one held is answered before its signature is checked,** since it could change nothing: the same serial `200`, a lower one `409 conflict`, and beside a revocation of the address it is left aside. Then `protocol.VerifyRevokedCertificates`, the function a client runs, and `protocol.VerifyRevocation` if the body carries one. **Everything checked is checked before anything is changed.** A check that fails counts under `-misses-per-minute`. **A raise is the identity's act,** counted against the box on a count of its own (`-certificate-revocations-per-day`), which no renewal spends.
- **The revocation of certificates is kept exactly as it was signed,** with its signature, in the address's revocations item (`revoked_certs`, `revoked_certs_sig`, and `through`, the serial it revokes through, which the write's condition reads), box or none, and is replaced whole by one through a higher serial: one `UpdateItem`, conditional on the `through` held being lower. One through a serial no higher than the one held is `409 conflict`, and the same one again writes nothing. It is three lines, so its size is fixed, and it is not in the box's record, so a renewal does not write it again.
- **What memory holds of it is one number per address,** the serial it revokes through: whether it covers the box's current certificate (`Standing.Listed`) is read off that and the record's `cert_serial`. So a poll is still answered with no read, and with nothing parsed.
- **What a revoked certificate loses here.** A call a box makes about itself, and a send from it, are `401 certificate_revoked` before any pass is looked at, a pass this server took a moment earlier included. A prekey upload under a revoked certificate is `401 certificate_revoked` before its pass is checked, the box's current statement sent again included. A send to a box whose current statement is under one is `409 prekey_expired` (§4, step 7).
- **The box's mail stays,** and the read of the box goes on serving the statement, beside the revocation that covers its certificate: the owner reads the mail after the renewal that brings the box back, and a sender that follows the statement is told `prekey_expired` at its send.
- **A revoked address takes nothing more** (`410`, §6.3). A body that carries both, for an address not yet revoked, has both kept, and the read of the box serves both in its `410`'s record.
- **With no box,** it is kept the same, and a registration of the address is held above it (§3).
- **Multi-process:** as §6.3. It reaches the other processes through the stream, and until it does a process that holds the box in memory answers for it as it was.
- **It is kept for good today:** none is dropped when the certificates it covers have ended.

## §6.4. Renewal: the order of checks, and the service limits

- **What could not be taken is refused before any signature is checked** (`prekey`). An identical retry is answered `200 {}` from the record, once its pass is checked under the box's current certificate, and changes nothing, the declared sender key types included. For any other statement, its place in the order is read without verifying it (`protocol.PrekeyOrder`: the statement's serial, and the serial and SHA-256 of the certificate its signature carries), and held to `PROTOCOL.md` §2b: a certificate of a higher serial, at any prekey serial, or the box's current certificate at a higher prekey serial (`409 conflict` if it is not higher). An older certificate, or another certificate of the current serial, is `401 certificate_not_current`, with the current one's serial in `certificate_serial`, and one the box's identity has revoked (§6.3a) `401 certificate_revoked`. So a replay of a box's public statement, in any bytes, costs no signature check.
- **Then the checks of registration** (§3 steps 4, 6 and 7), a count of misses reserved for them: the statement and its certificate, then the pass under that certificate. What they verify must read as the order read unverified did, or it is `bad_key`. The box's calls are then spent. It **refuses a key equal to the current one or to any live retired one** (`400 prekey_not_new`: "every prekey must be a NEW key"). The new prekey becomes current, its certificate becomes the box's current one, its record's expiry moves (§7), and the answer is `200 {}`; a declaration is replaced by a new prekey's, with none if that prekey brings none. A deleted box is `404`: a registration undoes the delete (§3).
- **Two numbers a day, each a budget reserved before the write** (`LIMITS.md`): a renewal under the box's current certificate takes from `-renewals-per-day`, and one under a later certificate, which only the identity can make, from `-certificates-per-day`, but for one while the box's current certificate is revoked, which replaces what a counted raise revoked (§6.3a) and takes from neither. So a holder of the current working key, who can make only the first kind, cannot spend the identity's way back. Past either, `429 rate_limited` naming `renewals` or `certificates`, with the number in `limit`, until one comes back; a refusal of the box's calls says the longer of the two waits. An identical retry is neither. The Go client makes a new certificate with every prekey, so its renewals are of the second kind. Each renewal is a write to the boxes table, whose capacity every box shares. **The record keeps its `-retired-kept` newest retired prekeys** (`RetiredKept`, a service limit), each until its `not_after`, so a box that renews often cannot grow it.

## §6.5. Accounts

- **`DELETE /v1/<A>/account`** (with the pass) → `204`, in an account or not. `irongall account leave`. An account drops a box the same way from its side (the operator's `irongalld account drop`, until accounts have users).
- **The adopt key** is `K = "iga1_" + base64url(account ‖ secret)`, no padding, with `secret` 32 random bytes. `irongalld account key` makes one and prints it, the one time it is shown: the server keeps its SHA-256 and never the key, as NIST SP 800-63B-4 §3.1.2.2 keeps a secret of 112 bits or more, with no salt. Its item is (`account`, `0x04` ‖ SHA-256(K)), and holds its uses left and its expiry. Adopt reads that item, strongly consistent, before anything is written, so a key that is not ours costs one read of the accounts table and no write of the box's record. A key that is not ours, spent, expired or deleted (revoked) is `403 adopt_key_refused`; a body with no key, a null one or an empty one is `400 bad_request`, naming `key` in `member`, as a missing member is. The box's record and the key's item are written in one transaction. One that meets another transaction on either item, as two adopts with one multi-use key do, is cancelled for a `TransactionConflict`, which the SDK does not retry: it applied nothing, so it is sent again by a new call, four calls in all with the SDK's own pauses for DynamoDB, and one that meets another every time is `409 box_changed`. A write of the record alone that meets the transaction (a leave, or any update of the box) is `409 box_changed` at once, as a failed condition is. A box already in the key's account is answered `200` and spends none, however many uses are left, so a retry whose answer was lost succeeds.
- **What an account changes:** an unmetered account's boxes (the echo account) have no daily send limit and the largest cap (`-account-max-size`), and are never charged. Until credit is built, a metered account's boxes have the free limits. Over the sender's own cap, a send is refused before its body is read.

## §7. Storage

**Three DynamoDB tables, one kind of thing each: boxes (`-boxes-table`), messages (`-msgs-table`) and accounts (`-accounts-table`).** An address's items in the boxes table are its box's record and its revocations, which one Query of the address reads together. A mail flood cannot throttle registration or rekey, boxes are backed up and mail is not, and each table's stream feeds its own cache.

| Where | Key | Holds | Expiry |
|---|---|---|---|
| the boxes table | `addr` = `H_B` (32 B binary), `sk` = `0x00` | box: the identity document, state (`active`, or `deleted` by its owner, §6.2), the current prekey statement + its signature (which carries the certificate; kept as it was sent, and at most its identity key type's bound, `protocol.SignatureBound`, as every signature on the record is, `PROTOCOL.md` §3), `cert_serial` and `cert` (that certificate's serial and the SHA-256 of its bytes), `senders` (the sender key types it declared with that statement), the `-retired-kept` newest retired prekeys' type, `not_after` and key hash (for the new-key rule), `rev` (`ARCHITECTURE.md`), created, `account` (the account it is in, if any), `acl` (the box's ACL as `GET …/acl` answers it: absent until the box puts one, then replaced whole by one of a higher version, §6.2), `expires_at` (when nothing of the box is valid any more, in seconds). Reserved and not written: warmup_until, profile + sig | TTL on `expires_at`: at a registration and each renewal, the later of its certificate's end and its prekey's `not_after` plus the mail TTL; at a delete, its certificate's end |
| the boxes table | `addr`, `sk` = `0x01` | the address's revocations, box or none: `identity`, `revocation` (the signature that revoked the address: written once and never removed; the record a box's read serves names it `revocation_signature`), `revoked_certs`, `revoked_certs_sig` and `through` (the identity's highest revocation of its certificates, as it was signed, its signature, and the serial it revokes through: absent until one is published, then replaced whole by one through a higher serial) | none |
| its GSI `account` | `account`, `addr` | keys only: each account's boxes, from the records that name one. A record that leaves its account, or that the TTL deletes, leaves it | with the record |
| the accounts table | `account` = the account id's bytes, `sk` = `0x00` | the account: `unmetered`, `rev` | none |
| the accounts table | `account`, `sk` = `0x04` ‖ SHA-256 of the key | an adopt key: `uses` left, `expires` (ms); never the key | TTL on `expires_at` |
| the boxes table | `addr` = `H_B`, `sk` ≥ `0x02` | reserved for the box's own items; none yet. The ACL's entries were once to be one item each here; they are in the record instead, bounded by `-acl-entries` (§6.2) | as the box |
| the messages table | `box` = `H_B`, `id` = SHA-256 of the ciphertext | one item per message, its header and its dedupe record: `from` (`H_A`, the box whose pass the send carried), size, received_at (ms), expires_at, and **`live` = received_at (ms, u64 big-endian) ‖ id while unacked**. No signature | TTL on expires_at — the item outlives an ack |
| its LSI `live` | `box`, `live` | the unacked messages only (an item without `live` is not in it), oldest first, with `from` and size: the list's cursor is the last `live` | with the item |
| S3 Express One Zone (a directory bucket in the server's AZ) | `<hex H_B>/<hex id>` | the binary age ciphertext, exactly as the send's body carried it | a lifecycle rule of at least the 33-day TTL, which needs the bucket policy below |

Boxes: PITR on, AWS Backup on, TTL on, stream `NEW_IMAGE`, the GSI `account`. Messages: neither backup, TTL on, stream `NEW_IMAGE`. Accounts: PITR on, AWS Backup on (billing data), TTL on, stream `NEW_IMAGE`. Every key is binary.

- **Send** (§4 steps 6 and 9). READ the item `box, id` first: a retry gets `200` and the original receipt, before anything about new mail. Then two plain writes, never a transaction:
  1. S3 `PUT` of the body;
  2. the message item, with the condition `attribute_not_exists(id) OR received_at <= now − TTL` (an expired item the TTL has not yet deleted is replaced).
  - **The key is content-addressed (`id = SHA-256(ciphertext)`), so a duplicate S3 PUT rewrites identical bytes — harmless.**
  - A crash after the S3 PUT leaves an orphan object, which the lifecycle rule reaps. That is normal. The sender got no `201`, so it retries, and the retry writes both.
  - **The header and the dedupe record are one item, so they cannot disagree:** every `200` and `201` means the message was stored. This replaced an earlier layout of three writes and the repair a retry needed when a crash fell between the dedupe record and the header (2026-10-11).
  - **A hit from ANOTHER `from` is answered `409`.** A `409` claims no delivery.
- **Cost per message:** one S3 Express PUT; the send's item write is 2 write units (the item, 190 B measured, and its LSI entry), the ack's 2 more (the update and the LSI entry's removal), and the dedupe read 1 read. The old layout wrote 3 units per message (dedupe record, header, then the header's delete): the LSI adds about $0.63 per million messages, at the on-demand price in AWS's offer file of 2026-09-11.
- **A box's item collection is capped at 10 GB** (every LSI's rule: its items and their index entries). An acked message's item is 146 B for 33 days (measured), so the cap is over 50 M messages per box per 33 days; a write past it fails with `ItemCollectionSizeLimitExceededException`. The per-sender limits put that out of reach.
- **Read:** the list Queries the LSI over the live key range (received_at > now − 33 days less an hour, `protocol.Retention`). `GET …/messages/<id>` reads the item by its key, and the S3 object through our endpoint — never a redirect — and answers its bytes as they are, `application/octet-stream` with a `Content-Length`: who sent it and when are the list's.
  - **A live item whose body is gone leaves the list, and is answered `no_such_message`.** This covers a half-finished ack, and a body that S3's lifecycle removed early (the timing on directory buckets was not checked).
  - **These reads are eventually consistent** (`ARCHITECTURE.md` § Memory): the conditional writes keep the data right, and a stale read costs a retry or one poll.
- **Ack:** delete the S3 object, then remove `live` from the item, with the condition that it is live and unexpired (otherwise `404`). Both steps are safe to repeat: a crash between them leaves a listed message with no body, which the client's next ack, or any fetch, takes out of the list. The item stays as the dedupe record until its TTL, so the server's dedupe spans the TTL even after an ack. **Close** does the same for every live message in the box.
- **The item's `expires_at` is the authority on expiry.** Lifecycle expiry is not exact: general purpose buckets round to the next midnight UTC, and the timing on directory buckets was not checked. So an object can outlive its item, and reads never serve a body whose item is gone.
- 🔴 **Lifecycle on a directory bucket needs a bucket policy** granting `lifecycle.s3.amazonaws.com` `s3express:CreateSession` with `s3express:SessionMode` = `ReadWrite`. Without it, nothing expires (AWS docs, *Working with S3 Lifecycle for directory buckets*). The server also reaches objects through `s3express:CreateSession`, not `s3:PutObject`.
- **Count cache:** in each process's memory, one mark per live message (id, sender, expiry, and how often this process served it), so counts stay exact without drift (`ARCHITECTURE.md` § Memory). Redis is penciled in for later. **A box's marks load on its first use by a process**, from a strongly consistent Query of the LSI, with its record and its revocations, read in one Query of the address — a box memory does not hold is never read as empty.

## §10. The echo box

- **Its identity key is kept and backed up** (identity keys may be), since losing it means a new address in every published place. **Its prekeys live in memory only** (a tmpfs), and it renews at every start: renewal needs only the identity (§6.4), and no prekey reaches a snapshot or backup.
- **No reply limit of its own**: it replies once per message, and every sender's own limits bound those. Its account lifts its daily send limit (§6.5); the server has no special case for it. ⚠ The per-IP pre-auth send rate (`-sends-per-minute-per-ip`, off by default) would count its replies too.

## §12. Not yet specified: the items that are this server's alone

- **Nothing in front of the server caches an API answer, the read of a box included: decided, and the server says so itself.** Every answer under `/v1/` carries `Cache-Control: no-store` (§6.3), whatever stands in front is set to do. So there is no lifetime and no purge to specify, and a new prekey, a close or a revocation is seen from the answer to the call that made it (this repo's issue #1, closed).
- **Legal posture** of an operator that holds only ciphertext.

## §13. 503 and logging

- **Every problem's `type` is its code's own,** `tag:irongall.dev,2026-10-17:errors/<code>` (`protocol.Code.TypeURI`, RFC 4151): a name, never a page to fetch. `api/apitest` fails a test server whose `type` is not its `code`'s.
- **`Retry-After` is always delay-seconds, in digits** (`retrySeconds`, rounded up), never an HTTP-date.
- **503** `unavailable`, with `Retry-After`: a process that cannot prove it is current with the change stream stops answering rather than answer wrong (`ARCHITECTURE.md`).
- **Logging**: no log line carries an address or a message id. Every run of 64 or more hex characters in a line, in a path or in a store's error, is written as `#` and the first 16 hex of the SHA-256 of the run in lower case (`redact`, on the writer under every log, net/http's own among them). The access log writes one line a request: the method, the path quoted, the status and the time taken; a method or a path longer than the longest path this server serves is written as its length alone. Passes and request bodies are never logged. A proxy or CDN in front (Cloudflare, for irongall.dev) DOES see addresses in URLs, in its own logs; revocation (§6.3) is the remedy for a leak. Pasting a share URL into a hosted chat also leaks it, to transcripts and link unfurlers.
