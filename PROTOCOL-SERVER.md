# PROTOCOL-SERVER — what this server does behind the spec

**The protocol's specification is [`PROTOCOL.md`](https://github.com/IronGall-dev/irongall-client/blob/main/PROTOCOL.md) in the client repo:** the wire, the checks and the refusals, as a client meets them. Every `PROTOCOL.md §N` in this repo's docs and code means that file. **This file holds how this server does each step** (storage, memory, measurements), under the spec's own section numbers. Read the spec's section first: a line here is a note beside it, not the whole of it.

**A change to the wire or to what a client meets is made in `PROTOCOL.md`, with the client code;** a change to how this server does it is made here.

## §0a, Terms

- **Identity key types:** the server registers the key types `-identity-types` names, of those this build verifies (`protocol.IdentityTypes`). `ssh-ed25519` is always one of them: the server does not start without it.
- **Address / `H`:** the box identity — the SHA-256 of its identity document (§2). As text, 64 lowercase hex characters; in DynamoDB keys, the 32 raw bytes. `H_A` is the sender, `H_B` the recipient. **One identity key ⇔ exactly one address.**
- **Header:** three different things. The **header item** is the per-message DynamoDB item (§7); the **age header** is the text head of an age file (§4.3); **HTTP headers** are HTTP headers.
- **The live prekey** is the current one: the server checks a message's stanza TYPE against its type (§4 step 7). The server keeps the newest retired prekeys' key hashes (`-retired-kept` of them, a service limit) only to refuse a key that comes back.

## §0b. A body is read as every reader reads JSON

- **Every request body goes through `decodeJSON`** (`internal/server/server.go`), which is the client repo's `protocol.UnmarshalRequest`: the same code the clients read answers with, on Go's `encoding/json/v2`. So the server and the clients hold one set of rules (`PROTOCOL.md` §0b) by one implementation. A byte field not in its one encoding is `bad_encoding`; anything else that breaks a rule is `bad_request`, and an unknown member is named in the `detail`, in the caller's own words.
- **What it costs:** the text is read twice, once for the rules `encoding/json/v2` leaves to its caller and once to decode it. Measured on one core here (Go 1.27.2): a send of 3 KiB of ciphertext, about 30 µs against 25 µs for the decoder it replaced; one of 1 MiB, about 8.2 ms against 7.0 ms.

## §3. Registration: steps 4 to 9 as this server does them

- **Step 4, the key's type:** `protocol.ParseIdentity` answers for the document's form, for a key type the protocol does not define, and for the key's checks. A key type that is not on this server's list is then answered `unsupported_key_type`, with the list in the detail. The list is of what the server can verify: it checks the identity's signature on every certificate it puts on record.
- **Step 5, before anything that costs** (`LIMITS.md`): a box this process holds is answered from its record (`Store.Known`), with no signature checked but an identical retry's pass. Any other registration takes from its address's registrations here (`-registrations-per-hour`), and that count is what bounds the signature checks after it: they reserve no count of misses of their own.
- **Steps 6 and 7 cost four signature checks:** the identity's on the certificate and the working key's on the statement (`protocol.VerifyPrekey`), then the pass, checked as every pass is (§6.1b): the working key's signature on it, and the identity's on the certificate once more. An identity's key type changes only the checks of its own signature: 58 µs each for Ed25519 and 81 µs for P-256 (measured 2026-10-13). A post-quantum statement's key check adds a trial wrap, an ML-KEM-768 encapsulation.
- **Step 6, the times:** a certificate that has not begun or has ended, and a statement that has expired or ends more than 33 days and an hour from the server's now (`protocol.MaxPrekeyLifetime`: an hour past what a client asks for, `PROTOCOL.md` §0), are `bad_key`, and each such answer states what the server's clock reads. A client makes both with an hour of room, so one of these is nearly always the caller's clock, and the hint says which way.
- **Step 8, a new box:** DynamoDB `PutItem` of the box item with `state: active`, the certificate's serial and the SHA-256 of its bytes, condition `attribute_not_exists(addr)` → `201 {}`. One write, and the box is in use: no call of its owner is needed first.
- **Step 9:** the record's `cert_serial` and `cert` are what later calls are held to (§6.1b, §6.4). Both are written with the statement they come from, in the same write, and so is `senders`: the sender key types the box declared with that statement (`PROTOCOL.md` §2c), of which the server keeps the names this build verifies, or `any` alone.

## §4.3a. Padding: the size limits are checked by hand

- **The server does nothing, and a size limit must be a whole number of its own blocks.** As sizes go, 64 KiB and 10 MiB are such numbers and 100 KiB is not: a message just under a limit like that one would be padded past it. With limits chosen that way a client never needs to know the limit. 🛑 Nothing checks this when `irongalld` starts: check `-max-size` and `-account-max-size` by hand before changing either.

## §4. The send pipeline: steps 1, 2 and 5 to 9

- **Step 1. The pass, before the body is read, and then the sender's calls.** The pre-auth rate per IP is taken first (`-sends-per-minute-per-ip`; an edge in front may have applied its own). Then the pass is parsed for the box it names, that box's standing is read (its state, its identity's key and its current certificate's hash: from memory if this process holds the box, otherwise from its record, §6.1b), and the pass is checked. The sender's record is then read for its account, from the record cache (the LRU of box records, `-box-cache`) or one `GetItem`: a pass that verified names a box that exists, so this read is not one `-misses-per-minute` counts. Then one of the sender's calls is spent (`-call-burst`, `LIMITS.md`), a retry's included: it bounds every step after it, the dedupe's read among them. A sender in no account is known to be so from memory, and spends it with nothing read.
- **Step 2. The read limit is the sender's own cap**, in base64 plus an allowance for the JSON. A body past the size of the free cap (`-max-size`) waits for the one allowance for large reads, and holds it until the send is answered: it bounds memory to one body of the largest cap. Only a sender whose account lifts its cap ever asks for it, since anyone else's body is refused at the free size. Nothing yet bounds how long a slow body holds it (this repo's issue #7).
- **Step 5. Is `B` registered and ACTIVE?** A lookup in memory, DynamoDB only on a cache miss, which reserves a count of misses for the caller's address (`LIMITS.md`). `B` unknown or closed → `no_such_mailbox`; `B` revoked → `revoked`.
- **Step 6. The dedupe:** one `GetItem` of the message item `box, id`, before anything about new mail is asked, so a retry gets its original receipt whatever has changed at `B` since. The read is bounded by step 1's calls, and a retry spends one.
- **Step 7. New mail on this prekey.** `B`'s current prekey past its `not_after` → `prekey_expired`, and the same for a current statement under a certificate `B`'s identity has revoked (§6.3a). That check parses the revocation of certificates in `B`'s record, so only a send to a box that has one pays for it.
- **Step 8. The counts, each reserved before the write and given back if nothing is stored:** the sender's sends a day; the pair and box caps, read from memory (not reserved: `LIMITS.md` § Known weaknesses); and `B`'s budget of new mail (`-receive-burst`), from all senders together, read with `B`'s account → `mailbox_busy`. An unmetered recipient has none.
- **Step 9. Write, body first** (§7): S3 `PUT` the body, then the message item, conditional on no live item with this id. Two plain writes, not a transaction.
  - If the condition fails, a concurrent send of the same ciphertext got there first. Answer as step 6 does.
  - Any other failure answers 5xx. The client keeps the message in its outbox and retries; the retry writes both again.
  - Then update memory, keep the counts step 8 reserved, and answer `201`.

**Step 7, the sender's key type, costs no read of its own.** The sender's type is line 2 of its identity document, in the record the send already holds for its account; what the recipient declared is in the recipient's record, which step 5 loads. A sender on an `ssh-ed25519` identity is never refused here.

**No signature on a message is checked on a send, and none is stored:** it is inside the ciphertext (`PROTOCOL.md` §4.4). What a send costs the server in signature checks is its pass, and only the first time that pass is shown (§6.1b).

## §5.1 and §5.7. Polls, pages and repeat fetches

- **`poll_after`** is the server's poll interval in seconds, `-poll-after` (GitHub's `X-Poll-Interval`). Bots are told that interval; what is enforced is `-poll-burst` at once and one more every `-poll-refill` (§8).
- Check the pass (§6.1b): for a box this process holds, from memory. **The per-box poll rate applies to EVERY poll, empty ones included** — an in-memory token bucket.
- **A list with a cursor is a continuation only if the box holds mail after the cursor.** Then it takes from the box's page allowance, not its polls: two full boxes' worth of pages at once, a full box's worth back every `-poll-refill` (the time one poll takes to come back, not `poll_after`), so a drain is never refused (§8). With nothing after the cursor it is a poll: it takes from the poll rate and is answered from memory with an empty page. So a cursor is no way around the poll rate.
- **If the in-memory count is 0, answer the empty body and touch nothing else.** An empty poll that carries a pass the server remembers measured 33 to 34 µs of server CPU, over loopback HTTP on one core, access log included; the same poll with the 62-byte bearer token it replaced measured 31 to 32 µs on the same machine (2026-10-13, `bench/README.md`). The check of the pass itself is 1.5 µs of that.
- Otherwise the page comes from one Query of the `live` index of the messages table (an in-process listing layer is planned and not built, `ARCHITECTURE.md` § Memory) — small entries keyed by `received_at`, so the Query returns time order and the cursor is the last key (§7). Small entries, because **DynamoDB bills a Query by the full size of each item read, projection or not** (AWS docs). → `ARCHITECTURE.md` § Memory.

**5.7 Ack:** `DELETE /v1/<B>/messages/<id>` deletes the S3 body and takes the message out of the list, and the counts follow. Its item stays as the dedupe record until the TTL. **Reading does NOT delete** — delivery is at-least-once, and unacked mail expires at the TTL. **But a message is meant to be fetched once and kept by its reader**: a message's first fetch is never limited, and a fetch of one the box has fetched before takes from an allowance of `-poll-burst` at once and one more every `-poll-refill`, the box's alone and apart from its polls; past it, `429 rate_limited` with `Retry-After`. Both clients store a message and ack it at once, so they meet the allowance only after a failure. The count is kept per process and a restart forgets it. The ack answers `204 No Content`. **A fetch or an ack of an id the box does not hold** is `404 no_such_message` from memory, and spends one of the box's calls (`LIMITS.md`): a held message's fetch and its ack were paid for by its receive.

## §6.1b. The pass, as this server checks it

- **What memory holds of each box it has loaded, for this check:** the box's state, its identity's key in SSH wire form (51 bytes for Ed25519, 104 for P-256) and the SHA-256 of its current certificate. With them a pass is checked with no read. The record itself holds the same, and is what a box this process has not loaded is checked against.
- **Before anything else, a value longer than any pass can be is refused,** `401 unauthorized`, before it is hashed or parsed: `protocol.MaxPassAuthorization`, 5,600 bytes, the length of a pass whose signature is the most a signature may be (`PROTOCOL.md` §3, §6.1b). A pass is 1,264 bytes. Go's own limit on all of a request's headers, 1 MiB, still applies to what is read.
- **A new pass is checked in three steps, cheapest first** (`checkPass`):
  1. **The certificate it carries, by the SHA-256 of its bytes, against the hash of the box's current one.** A pass under any other certificate is refused here, with no signature check. Another encoding of the same certificate, which one signed by an ECDSA identity has (`PROTOCOL.md` §2b), is other bytes, and is refused here too.
  2. **The working key's signature on the pass.** A certificate is public, since it rides in everything a box signs, and a signature does not cover the key it names: anyone can name a box's certificate in a pass of their own. This step is what refuses that.
  3. **The identity's signature on the certificate, and every rule of `PROTOCOL.md` §2b's table,** as when the certificate was put on record. It is reached only by a pass the working key signed. It checks again what a registration or a prekey upload checked, so a record that held the hash of a certificate its identity never signed would still give no pass. If it ever fails, the record is wrong: the server logs it and answers `401` with the hint to publish a new prekey, which is checked in full.
- **A pass that passed is remembered until it runs out, or until its certificate ends if that is sooner:** per box, the SHA-256 of the `Authorization` value, the certificate it was checked under, and that moment. A later call with the same value, while the box's current certificate is still that one, is a hash of the header and a lookup: 1.5 µs measured. The first check is those three steps, two signature checks in all: about 180 µs measured (`internal/server/cost_test.go`). So a box that keeps its pass for ten minutes, as both clients do, costs one such check in ten minutes of calls.
- **One pass is remembered per box, the last it showed.** Two clients running one box with different passes would each be checked again on every call; the clients here keep one pass in the box's state directory.
- **A pass that has run out is never taken again, and its entry is dropped at the next sweep,** which runs when a pass is kept and at most once an hour. So the map holds only boxes that showed a pass within about the last two hours. It is 168 bytes a box (measured).
- **The server's names are a setting, `-names`:** a pass is checked against the request's `Host`, in lowercase, and only if that is one of them. The name is not sent with the pass, so a server that took whatever name a request gave would take a pass made for another server. A proxy in front must pass `Host` on unchanged. `--dev` takes any name unless `-names` is given. A pass the server remembers was checked this way when it was first shown, and is taken after that whatever `Host` a later request carries.
- **The order of the answers, for a call a box makes about itself** (list, fetch, ack, close, adopt, leave): the box's state first (`404`, `410`), then the pass, so a call naming a box that is closed or revoked is told so whatever it carries. A box whose current certificate its identity has revoked (§6.3a) is answered `401` next, before any pass is looked at. **A send** has to read a pass to know whose it is, so one that is not a pass is `401` first; then its box's state answers (`403 unknown_sender` or `sender_revoked`), then the pass. **A registration** follows the spec's order: the statement, the pass, then whether the box exists. **A prekey upload** answers first for a box that does not exist or is revoked, then for the statement, then for the pass.
- **Run out, or running out more than an hour ahead,** is `401 pass_expired`, and is decided before any signature is checked. The detail states what the server's clock reads, and the hint which way the caller's is off if a new pass is refused too: 10 minutes or more behind, or more than 50 ahead (`PROTOCOL.md` §0). The hint says to check that clock, never to set it by the server's. **Every answer is dated by the clock the checks read** (`Server.dated`), so a client can set the `Date` beside its own. Anything else wrong with a pass is `401 unauthorized`: not a pass, another box's, made for another name, a signature that does not verify, or a certificate that is not the box's current one.
- **A pass this process has not seen reserves a count of its caller's address first** (`-misses-per-minute`, `LIMITS.md`), kept if the pass fails and given back if it passes, and so does an `Authorization` value that is no pass: past the count, a new pass is refused before it is checked. One the process remembers is not counted. One under any certificate but the box's current one stops at step 1: 35 µs measured, a parse and two hashes. One that carries the box's current certificate, which every correspondent of the box has seen, stops at step 2: 95 µs, one signature check. A registration's pass is bounded by the count of registrations instead (§3).
- **Multi-process:** a box's move to a new certificate reaches the other processes through the DynamoDB stream (`ARCHITECTURE.md`; 1 to 2 s). Until it does, a process still takes a pass under the certificate before it. That window is stated, not hidden.
- **The server keys `K_kid`** now make adopt keys only (§6.5): 32 random bytes each, `kid` a u8 allocated sequentially, kept in a 0600 file every process is given (`-keys`). Adopt keys are minted with the highest `kid` and checked with any key the file holds.

## §6.3. Revocation, as this server does it

- **The route checks in this order** (`revoke`): the calls with no pass of the caller's address (`-public-burst`); the body's fields; that the document hashes to the address in the path; the box's record, from memory or by one read. **Then, before any signature is checked, what could change nothing:** anything for a box already revoked is `410 revoked`, the body unread beyond its form. Then one signature check, `protocol.VerifyRevocation`, the function a client runs. No pass is read.
- **A signature check reserves a count of the caller's address first** (`-misses-per-minute`), kept if the body does not verify and given back if it does: it costs a check that nothing else paid for. Past the count, a caller is refused before the check, a revocation that would have verified included, until a count comes back. The revocation of an address is counted by nothing else.
- **The record is written first, then the box's mail is deleted** (`DeleteMessages`): the state `revoked`, with the signature in `revocation`. A send that had passed its recipient check before the write can still land after the delete. It is never served, since every call naming the box now answers `410`, and it goes at its expiry. Anything sent again for the box is `410`, and deletes again only while memory shows the box holding mail: a retry of one whose delete failed does, and one sent back at an empty box, in whatever bytes, draws no read of the messages table.
- **The signature is kept in the box's record for good,** beside the identity document already there, and `GET …/revocations` serves the two. Nothing about a revoked box lives only in the memory of the process that took the revocation: another process, or this one after a restart, serves the same record (tested on DynamoDB).
- **This server is a revocation server for the boxes it has, and for no other address** (`PROTOCOL.md` §6.3, "Revocation servers"): a record for an address it never registered is `404 no_such_mailbox`. One that answers for any address is a program of its own, with no boxes and none of this server's code: the reference one is in the client repo (`revocationserver/`, `cmd/irongall-revocation-server`). A client publishes to both by itself, and this server passes a revocation on to nobody.
- **A client's lookup before a post** (`PROTOCOL.md` §4.1) costs no read of the boxes table that a send did not already cost. `GET …/revocations` is answered from the record cache, and the record is served as it is kept, with nothing parsed. For a box this process has not loaded, the lookup makes the one read that the `/identity` call after it would have made, and that call is then answered from memory. Like `/identity` it is counted against the box whose pass it carries, or against its caller's address with none (`LIMITS.md`).
- **Multi-process:** the change reaches the other processes through the DynamoDB stream, as a new certificate does (§6.1b). Until it does, a process that holds the box in memory still answers for it as it was.
- **Every answer under `/v1/` carries `Cache-Control: no-store`** (`notStored`), so nothing in front may serve a box's identity, its prekey or a `410` again. A `410` is cacheable by default.
- **Not built:** a standalone index.

## §6.3a. Certificates revoked, as this server does it

- **The same route, and the same order of checks** as §6.3 (`revoke`): the body's fields, which are the document and then a revocation of certificates with its signature, a revocation of the address, or both; that the document hashes to the address; the box's record. **A revocation of certificates through a serial no higher than the one held is answered before its signature is checked,** since it could change nothing: the same serial `200`, a lower one `409 conflict`, and beside a revocation of the address it is left aside. Then `protocol.VerifyRevokedCertificates`, the function a client runs, and `protocol.VerifyRevocation` if the body carries one. **Everything checked is checked before anything is changed.** A check that fails counts under `-misses-per-minute`. **A raise is the identity's act,** counted against the box with its renewals under a later certificate (`-identity-acts-per-day`).
- **The revocation of certificates is kept exactly as it was signed,** with its signature, in the box's record (`revoked_certs`, `revoked_certs_sig`), and is replaced whole by one through a higher serial: one write, conditional on the record's revision as every other is. One through a serial no higher than the one held is `409 conflict`, and the same one again writes nothing. It is three lines, so its size is fixed.
- **What memory holds of it is one fact:** whether it covers the box's current certificate (`Standing.Listed`), worked out when the record is written or loaded. So a poll is still answered with no read, and with nothing parsed.
- **What a revoked certificate loses here.** A call a box makes about itself, and a send from it, are `401 unauthorized` before any pass is looked at, a pass this server took a moment earlier included. A prekey upload under a revoked certificate is `bad_key` before its pass is checked, the box's current statement sent again included. A send to a box whose current statement is under one is `409 prekey_expired` (§4, step 7).
- **The box's mail stays,** and `GET …/identity` goes on serving the statement: the owner reads the mail after the renewal that brings the box back, and a sender that follows the statement is told `prekey_expired` at its send.
- **A revoked box takes nothing more** (`410`, §6.3). A body that carries both, for a box not yet revoked, has both kept, and `GET …/revocations` serves both.
- **Multi-process:** as §6.3. It reaches the other processes through the stream, and until it does a process that holds the box in memory answers for it as it was.
- **It is kept for good today:** none is dropped when the certificates it covers have ended.

## §6.4. Renewal: the order of checks, and the service limits

- **What could not be taken is refused before any signature is checked** (`prekey`). An identical retry is answered `200 {}` from the record, once its pass is checked under the box's current certificate, and changes nothing, the declared sender key types included. For any other statement, its place in the order is read without verifying it (`protocol.PrekeyOrder`: the statement's serial, and the serial and SHA-256 of the certificate its signature carries), and held to `PROTOCOL.md` §2b: a certificate of a higher serial, at any prekey serial, or the box's current certificate at a higher prekey serial (`409 conflict` if it is not higher). An older certificate, another certificate of the current serial, and one the box's identity has revoked (§6.3a) are `bad_key`. So a replay of a box's public statement, in any bytes, costs no signature check.
- **Then the checks of registration** (§3 steps 4, 6 and 7), a count of misses reserved for them: the statement and its certificate, then the pass under that certificate. What they verify must read as the order read unverified did, or it is `bad_key`. The box's calls are then spent. It **refuses a key equal to the current one or to any live retired one** (`bad_key`: "every prekey must be a NEW key"). The new prekey becomes current, its certificate becomes the box's current one, a closed box is `active` again, and the answer is `200 {}`; a declaration is replaced by a new prekey's, with none if that prekey brings none.
- **Two counts by UTC day, reserved before the write** (`LIMITS.md`): a renewal under the box's current certificate takes from `-renewals-per-day`, and one under a later certificate, which only the identity can make, from `-identity-acts-per-day`, which a raise of the revocation of certificates shares (§6.3a). So a holder of the current working key, who can make only the first kind, cannot spend the identity's way back. Past either, `429 rate_limited` until the next day; an identical retry is neither. The Go client makes a new certificate with every prekey, so its renewals are of the second kind. Each renewal is a write to the boxes table, whose capacity every box shares. **The record keeps its `-retired-kept` newest retired prekeys** (`RetiredKept`, a service limit), each until its `not_after`, so a box that renews often cannot grow it.

## §6.5. Accounts

- **`DELETE /v1/<A>/account`** (with the pass) → `204`, in an account or not. `irongall adopt --leave`. An account drops a box the same way from its side (the operator's `irongalld account drop`, until accounts have users).
- **The adopt key** is computed, never stored: `K = "iga1_" + base64url(kid ‖ id ‖ n ‖ account ‖ mac)`, no padding, with `id` 16 random bytes, `n` the account id's length (a u8) and `mac = HMAC-SHA-256(K_kid, "irongall-adopt-v1" ‖ kid ‖ id ‖ n ‖ account)`. The account's table holds only the key's uses left and its expiry. A key that is not ours, spent, expired or deleted (revoked) is `403 adopt_key_refused`.
- **What an account changes:** an unmetered account's boxes (the echo account) have no daily send limit and the largest cap (`-account-max-size`), and are never charged. Until credit is built, a metered account's boxes have the free limits. Over the sender's own cap, a send is refused before its body is read.

## §7. Storage

**Three DynamoDB tables, one kind of thing each: boxes (`-boxes-table`), messages (`-msgs-table`) and accounts (`-accounts-table`).** A mail flood cannot throttle registration or rekey, boxes are backed up and mail is not, and each table's stream feeds its own cache.

| Where | Key | Holds | Expiry |
|---|---|---|---|
| the boxes table | `addr` = `H_B` (32 B binary), `sk` = `0x00` | box: the identity document, state (active / closed / revoked), the current prekey statement + its signature (which carries the certificate; kept as it was sent, and at most `protocol.MaxSignature` bytes, as every signature on the record is, `PROTOCOL.md` §3), `cert_serial` and `cert` (that certificate's serial and the SHA-256 of its bytes), `senders` (the sender key types it declared with that statement), the `-retired-kept` newest retired prekeys' type, `not_after` and key hash (for the new-key rule), `rev` (`ARCHITECTURE.md`), created, `account` (the account it is in, if any), `revocation` (the signature that revoked the box: written once, when it is revoked, and never removed), `revoked_certs` and `revoked_certs_sig` (the identity's highest revocation of its certificates, as it was signed, and its signature: absent until one is published, then replaced whole by one through a higher serial). Reserved and not written: warmup_until, profile + sig, allow, block | none |
| the accounts table | `account` = the account id's bytes, `sk` = `0x00` | the account: `unmetered`, `rev` | none |
| the accounts table | `account`, `sk` = `0x01` ‖ `H_B` | a box the account holds: the mirror of the box record's `account`, written with it in one transaction | none |
| the accounts table | `account`, `sk` = `0x04` ‖ key id | an adopt key: `uses` left, `expires` (ms); no secret | TTL on `expires_at` |
| the boxes table | `addr` = `H_B`, `sk` ≠ `0x00` | reserved for the box's own items (allow/block entries one item each, so no list grows toward DynamoDB's 400 KB item limit); none yet | as the box |
| the messages table | `box` = `H_B`, `id` = SHA-256 of the ciphertext | one item per message, its header and its dedupe record: `from` (`H_A`, the box whose pass the send carried), size, received_at (ms), expires_at, and **`live` = received_at (ms, u64 big-endian) ‖ id while unacked**. No signature | TTL on expires_at — the item outlives an ack |
| its LSI `live` | `box`, `live` | the unacked messages only (an item without `live` is not in it), oldest first, with `from` and size: the list's cursor is the last `live` | with the item |
| S3 Express One Zone (a directory bucket in the server's AZ) | `<hex H_B>/<hex id>` | the binary age ciphertext, exactly as decoded from the send | a lifecycle rule of at least the 33-day TTL, which needs the bucket policy below |

Boxes: PITR on, AWS Backup on, stream `NEW_IMAGE`. Messages: neither backup, TTL on, stream `NEW_IMAGE`. Accounts: PITR on, AWS Backup on (billing data), TTL on, stream `NEW_IMAGE`. Every key is binary.

- **Send** (§4 steps 6 and 9). READ the item `box, id` first: a retry gets `200` and the original receipt, before anything about new mail. Then two plain writes, never a transaction:
  1. S3 `PUT` of the body;
  2. the message item, with the condition `attribute_not_exists(id) OR received_at <= now − TTL` (an expired item the TTL has not yet deleted is replaced).
  - **The key is content-addressed (`id = SHA-256(ciphertext)`), so a duplicate S3 PUT rewrites identical bytes — harmless.**
  - A crash after the S3 PUT leaves an orphan object, which the lifecycle rule reaps. That is normal. The sender got no `201`, so it retries, and the retry writes both.
  - **The header and the dedupe record are one item, so they cannot disagree:** every `200` and `201` means the message was stored. This replaced an earlier layout of three writes and the repair a retry needed when a crash fell between the dedupe record and the header (2026-10-11).
  - **A hit from ANOTHER `from` is answered `409`.** A `409` claims no delivery.
- **Cost per message:** one S3 Express PUT; the send's item write is 2 write units (the item, 190 B measured, and its LSI entry), the ack's 2 more (the update and the LSI entry's removal), and the dedupe read 1 read. The old layout wrote 3 units per message (dedupe record, header, then the header's delete): the LSI adds about $0.63 per million messages, at the on-demand price in AWS's offer file of 2026-09-11.
- **A box's item collection is capped at 10 GB** (every LSI's rule: its items and their index entries). An acked message's item is 146 B for 33 days (measured), so the cap is over 50 M messages per box per 33 days; a write past it fails with `ItemCollectionSizeLimitExceededException`. The per-sender limits put that out of reach.
- **Read:** the list Queries the LSI over the live key range (received_at > now − 33 days). `GET …/messages/<id>` reads the item by its key, and the S3 object through our endpoint — never a redirect — and returns the body base64 in JSON.
  - **A live item whose body is gone leaves the list, and is answered `no_such_message`.** This covers a half-finished ack, and a body that S3's lifecycle removed early (the timing on directory buckets was not checked).
  - **These reads are eventually consistent** (`ARCHITECTURE.md` § Memory): the conditional writes keep the data right, and a stale read costs a retry or one poll.
- **Ack:** delete the S3 object, then remove `live` from the item, with the condition that it is live and unexpired (otherwise `404`). Both steps are safe to repeat: a crash between them leaves a listed message with no body, which the client's next ack, or any fetch, takes out of the list. The item stays as the dedupe record until its TTL, so the server's dedupe spans the TTL even after an ack. **Close** does the same for every live message in the box.
- **The item's `expires_at` is the authority on expiry.** Lifecycle expiry is not exact: general purpose buckets round to the next midnight UTC, and the timing on directory buckets was not checked. So an object can outlive its item, and reads never serve a body whose item is gone.
- 🔴 **Lifecycle on a directory bucket needs a bucket policy** granting `lifecycle.s3.amazonaws.com` `s3express:CreateSession` with `s3express:SessionMode` = `ReadWrite`. Without it, nothing expires (AWS docs, *Working with S3 Lifecycle for directory buckets*). The server also reaches objects through `s3express:CreateSession`, not `s3:PutObject`.
- **Count cache:** in each process's memory, one mark per live message (id, sender, expiry, and how often this process served it), so counts stay exact without drift (`ARCHITECTURE.md` § Memory). Redis is penciled in for later. **A box's marks load on its first use by a process**, from a strongly consistent Query of the LSI, with its record — a box memory does not hold is never read as empty.

## §10. The echo box

- **Its identity key is kept and backed up** (identity keys may be), since losing it means a new address in every published place. **Its prekeys live in memory only** (a tmpfs), and it renews at every start: renewal needs only the identity (§6.4), and no prekey reaches a snapshot or backup.
- **No reply limit of its own**: it replies once per message, and every sender's own limits bound those. Its account lifts its daily send limit (§6.5); the server has no special case for it. ⚠ The per-IP pre-auth send rate (`-sends-per-minute-per-ip`, off by default) would count its replies too.

## §12. Not yet specified: the items that are this server's alone

- **Nothing in front of the server caches an API answer, `/identity` included: decided, and the server says so itself.** Every answer under `/v1/` carries `Cache-Control: no-store` (§6.3), whatever stands in front is set to do. So there is no lifetime and no purge to specify, and a new prekey, a close or a revocation is seen from the answer to the call that made it (this repo's issue #1, closed).
- **Legal posture** of an operator that holds only ciphertext.

## §13. 503 and logging

- **503** `unavailable`, with `Retry-After`: a process that cannot prove it is current with the change stream stops answering rather than answer wrong (`ARCHITECTURE.md`).
- **Logging**: the access log never carries a full address — hash it (e.g. the first 16 hex of SHA-256 of the address) or redact it. Passes and request bodies are never logged. A proxy or CDN in front (Cloudflare, for irongall.dev) DOES see addresses in URLs, in its own logs; revocation (§6.3) is the remedy for a leak. Pasting a share URL into a hosted chat also leaks it, to transcripts and link unfurlers.
